# Loyalty Program

The Slices loyalty program rewards users who contribute to the platform's growth. It consists of two parts:

- **[Referral Program](/docs/loyalty/referrals)** — earn rewards by referring new users
- **[Airdrop Data](/docs/loyalty/airdrop)** — what on-chain activity is tracked for future distributions

## How It Works

The loyalty service tracks every fee-paying action per user by processing on-chain events through a multi-stage pipeline.

### Event Flow

1. **blockchain-scanner** (external service) listens to on-chain events from smart contracts: `Pool.mint()` / `Pool.burn()`, `TokenFactory` (RWA creation), `PoolFactory` (pool creation), and `ReferralTreasury` (withdrawals)
2. The scanner publishes each event to the RabbitMQ queue `blockchain.events.loyalty`
3. **BlockchainEventsDaemon** (internal daemon of the loyalty service) is subscribed to this queue, receives events, and processes them
4. The daemon writes the processed data to MongoDB

### Fee Processing

When a user pays a fee (creation, buy, sell), the system:

1. Checks if the user has a registered referrer
2. Records the commission amount in the user's fee history
3. Calculates a referral reward for the referrer (a percentage of the commission)
4. Stores everything in a queryable database for transparency

### ReferralTreasury Event Processing

When a user withdraws rewards via multi-signature, the `ReferralTreasury` contract emits the `ReferralTreasury_Withdrawn` event. The blockchain-scanner picks it up, publishes it to RabbitMQ, and the daemon processes it by updating the `totalWithdrawnAmount` field in the `referrerWithdraws` collection. This allows the system to track the actual amount withdrawn by each user.

## ReferralTreasury Contract

All referral rewards are stored in the **ReferralTreasury** smart contract. This contract holds USDT and is funded **manually** by the protocol — there is no automatic minting or top-up. This means the total reward pool is limited by what has been deposited into the treasury.

Withdrawals from the treasury require **multi-signature approval** from authorized signers, the same system used for RWA and pool deployments.

The contract emits the `ReferralTreasury_Withdrawn` event upon a successful withdrawal. This event is picked up by the blockchain-scanner, published to RabbitMQ, and processed by the loyalty service's `BlockchainEventsDaemon` to synchronize the withdrawal status — specifically updating the `totalWithdrawnAmount` field in the `referrerWithdraws` collection.

## Architecture

The Loyalty Service is a microservice built with the following components:

```
┌─────────────────────────────────────────────────────┐
│                 blockchain-scanner                   │
│  External service — listens to on-chain events from │
│  smart contracts: Pool, TokenFactory, PoolFactory,  │
│  ReferralTreasury, and publishes to RabbitMQ        │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│                    RabbitMQ                         │
│          queue: blockchain.events.loyalty            │
└──────────────────┬──────────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│              Blockchain Events Daemon                │
│  Internal daemon of the Loyalty Service — reads from │
│  RabbitMQ, processes events, writes to MongoDB      │
│  Events handled:                                    │
│  • Factory_CreateRWAFeeCollected                    │
│  • Factory_CreatePoolFeeCollected                   │
│  • Pool_RwaMinted                                   │
│  • Pool_RwaBurned                                   │
│  • ReferralTreasury_Withdrawn                       │
└──────────────────┬──────────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│                    MongoDB (5 collections)           │
│  • commissionHistory  — audit log of all fees       │
│  • fees               — aggregated fee data         │
│  • referrals          — referral relationships       │
│  • referrerClaimHistory — referral reward history    │
│  • referrerWithdraws  — withdrawal requests          │
└──────────────────┬──────────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│              Loyalty Service (Elysia/Bun)            │
│  7 REST POST endpoints for data querying             │
└──────────────────┬──────────────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────────────┐
│                 SignersManager                       │
│  External service for multi-signature task creation  │
└─────────────────────────────────────────────────────┘
```

### Components

| Component | Technology | Purpose |
|-----------|-----------|---------|
| **blockchain-scanner** | External service | Listens to on-chain events and publishes them to RabbitMQ |
| **HTTP Server** | Elysia (Bun) | Serves REST API endpoints |
| **Database** | MongoDB (Mongoose) | Stores all loyalty data |
| **Message Queue** | RabbitMQ | Delivers blockchain events to the daemon |
| **Blockchain Events Daemon** | Background process (internal) | Reads from RabbitMQ, processes events, writes to DB |
| **SignersManager** | External service | Creates multi-signature tasks for withdrawals |
| **Eden** | External service | Executes on-chain transactions |

## REST API Endpoints

All endpoints accept `POST` requests with a JSON body and return JSON responses.

| Endpoint | Description |
|----------|-------------|
| `POST /getFees` | Get aggregated fee data for a user (per chain, per token) |
| `POST /getCommissionHistory` | Get detailed audit log of all commission events |
| `POST /getReferrals` | Get referral relationships for a user |
| `POST /registerReferral` | Register a new referral relationship |
| `POST /getReferrerClaimHistory` | Get history of referral rewards earned |
| `POST /createReferrerWithdrawTask` | Create a withdrawal request for referral rewards |
| `POST /getReferrerWithdraws` | Get status of withdrawal requests |

## Data Models

All data is stored in MongoDB in five collections described below. Each model corresponds to a Mongoose schema with indexes.

### Commission History

Audit log of every fee-paying event with on-chain transaction hash for verifiability.

| Field | Type | Description |
|-------|------|-------------|
| `id` | `ObjectId` | Unique record identifier |
| `userWallet` | `string` | Wallet address that paid the fee |
| `userId` | `string` | Platform user ID |
| `chainId` | `number` | Blockchain ID |
| `tokenAddress` | `string` | Token address of the fee (e.g. USDT) |
| `amount` | `Decimal128` | Fee amount |
| `actionType` | `string` | One of: `buy_commission`, `sell_commission`, `token_creation_commission`, `pool_creation_commission`, `referral_reward` |
| `transactionHash` | `string` | On-chain transaction hash for auditability |
| `relatedUserWallet` | `string?` | Referred user's wallet (for referral rewards) |
| `relatedUserId` | `string?` | Referred user's platform ID (for referral rewards) |
| `createdAt` | `Date` | Record creation timestamp |
| `updatedAt` | `Date` | Record update timestamp |

## Withdrawal Mechanism

### Creating a Withdrawal Request

When a user requests a withdrawal of referral rewards via `POST /createReferrerWithdrawTask`:

1. The system validates the `chainId` against the list of **supported networks**
2. A **message hash** is generated using `ethers.solidityPackedKeccak256` with the user's wallet, chain ID, token address, and amount
3. The withdrawal task is sent to **Eden** (external service) for on-chain execution
4. A record is created in the `referrerWithdraws` collection with the task ID

### Cooldown

- There is a **30-day cooldown** (`60 × 60 × 24 × 30` seconds) between withdrawal requests
- The `taskCooldown` field stores this value
- The `taskExpiredAt` field stores the timestamp when the current task expires

### Multi-Signature

- Withdrawals require **multi-signature approval** from authorized signers
- The **SignersManager** external service handles the creation of signing tasks
- This is the same multi-signature system used for RWA and pool deployments

### Tracking Withdrawals

Users can track their withdrawal requests via `POST /getReferrerWithdraws`, which returns the list of records from the `referrerWithdraws` collection.

## Key Data Tracked

The loyalty service tracks the following per user, per chain, per token:

| Metric | Description |
|--------|-------------|
| Buy commissions | Total fees paid when buying RWA tokens |
| Sell commissions | Total fees paid when selling RWA tokens |
| RWA creation commissions | Fees paid when deploying RWA tokens |
| Pool creation commissions | Fees paid when deploying pools |
| Referral rewards | Rewards earned from referred users' fees |
| Referral relationships | Who referred whom |

This data can be used for **future airdrop calculations** — see [Airdrop Data](/docs/loyalty/airdrop) for details.
