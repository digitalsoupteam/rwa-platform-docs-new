# Proposals

Proposals are the mechanism for making changes to the Slices protocol through decentralized governance. Any staker with sufficient voting power can create a proposal to execute an arbitrary contract call.

## Proposal Types

Proposals can target any contract call. Common proposal types include:

- **Parameter changes** — updating fee ranges, period durations, or other Config parameters
- **Contract upgrades** — upgrading contract implementations via UUPS
- **Treasury management** — withdrawing funds from the Treasury
- **Signer management** — adding or removing authorized signers
- **Emergency actions** — pausing contracts or other safety measures

## Creating a Proposal

To create a proposal, you need sufficient voting power (above the `proposalThreshold` set in Config):

```solidity
function propose(
    address target,      // Contract to call
    bytes memory data,   // Encoded function call
    string memory description  // Human-readable description
) external returns (uint256 proposalId)
```

```javascript
// Encode the target function call
const data = config.interface.encodeFunctionData("updateEntryFeePercentRange", [50, 500]);

// Create proposal
const tx = await governance.propose(
  configAddress,    // target contract
  data,             // encoded function call
  "Reduce entry fee range from 100-1000 to 50-500 bps"  // description
);
const receipt = await tx.wait();
const proposalId = ... // parse from event
```

To vote on a proposal, call the `vote` function:

```solidity
function vote(
    uint256 proposalId,  // ID of the proposal
    bool support,        // true = for, false = against
    string memory reason // Arbitrary string with voting justification
) external
```

The `reason` parameter is an arbitrary string that provides justification for the vote. It is emitted in the `Governance_VoteCast` event for transparency.

The proposal starts immediately with `endTime = block.timestamp + votingPeriod`. There is no voting delay — voting begins right away.

## Proposal Lifecycle

```
Created → Voting Period → Auto-Executed or Auto-Cancelled
```

1. **Created** — a user with sufficient voting power calls `propose()`
2. **Voting** — stakers vote for or against during the voting period
3. **Auto-execution** — checked after each vote: if `votesFor >= quorum` AND `votesFor > votesAgainst` → the proposal executes immediately by calling `target.call(data)`. If the target call reverts, the error message is decoded using `_getRevertMsg` and the transaction reverts with that message.
4. **Auto-cancellation** — if `votesAgainst >= quorum` AND `votesAgainst > votesFor` → the proposal is cancelled immediately
5. **Manual cancellation** — the proposer can cancel within 12 hours of creation

## Quorum & Thresholds

| Parameter | Value | Description |
|----------|-------|-------------|
| **Proposal threshold** | **1,000,000** PlatformToken | Minimum stake to create a proposal (`proposalThreshold`) |
| **Quorum** | **40%** of totalVotingPower (total staked tokens) | Minimum participation for proposal to pass (`quorumPercentage = 4000 bps`) |
| **Voting period** | **7 days** | Duration of voting (`votingPeriod`) |
| **Voting delay** | **0** | Delay before voting begins (`votingDelay`) |
| **Timelock delay** | **2 days** | Mandatory delay for sensitive operations (`timelockDelay`) |

For example, if total staked PlatformToken = **10,000,000**, quorum = 10,000,000 × 40% = **4,000,000 votes**. To pass, a proposal needs `votesFor >= 4,000,000` AND `votesFor > votesAgainst`.

To create a proposal, you must have **≥ 1,000,000 PlatformToken** staked. If you have 500,000 — you can only vote on others' proposals, not create your own.

## Timelock Controller

The Timelock controller adds a mandatory delay for sensitive operations (e.g., Treasury withdrawals). The delay is set via `config.timelockDelay()` (default 2 days).

```solidity
// Queue a transaction for execution
function queueTransaction(
    address target,
    bytes memory data,
    uint256 eta       // Unix timestamp when execution becomes available
) external            // requires addressBook.requireGovernance(msg.sender)

// Execute a queued transaction (anyone can call once eta is reached)
function executeTransaction(
    address target,
    bytes memory data,
    uint256 eta
) external            // no access control — anyone can execute

// Cancel a queued transaction
function cancelTransaction(
    address target,
    bytes memory data,
    uint256 eta
) external            // requires addressBook.requireGovernance(msg.sender)

// Withdraw ERC20 tokens from Timelock (only callable by Timelock role)
function withdrawERC20(address token, address to, uint256 amount) external

// Withdraw ETH from Timelock (only callable by Timelock role)
function withdrawETH(address to, uint256 amount) external
```

**Key points:**
- Governance calls `queueTransaction` to schedule an operation
- After `eta` is reached, **anyone** can call `executeTransaction` (no access control)
- The transaction must be executed within `GRACE_PERIOD = 7 days` after `eta`, otherwise it expires
- `timelockDelay` is used to set the minimum `eta` when queuing
- `withdrawERC20` and `withdrawETH` are used to recover tokens or ETH that were mistakenly sent to the Timelock contract. Both functions are only callable by an address with the Timelock role.

## Events

All governance events are emitted through the `EventEmitter` contract:

| Event | Parameters |
|-------|-----------|
| `Governance_ProposalCreated` | `uint256 proposalId, address proposer, address target, bytes data, string description, uint256 creationTime, uint256 endTime, bool executed, bool cancelled` |
| `Governance_VoteCast` | `uint256 proposalId, address voter, bool support, uint256 votes, string reason` |
| `Governance_ProposalCancelled` | `uint256 proposalId, address canceller` |
| `Governance_ProposalExecuted` | `uint256 proposalId, address executor` |

## Data Structures

### Proposal

```solidity
struct Proposal {
    address proposer;      // Creator of the proposal
    address target;        // Contract to call
    bytes data;            // Encoded function call
    string description;    // Human-readable description
    uint256 votesFor;      // Total votes in favor
    uint256 votesAgainst;  // Total votes against
    uint256 creationTime;  // Timestamp when created
    uint256 endTime;       // Timestamp when voting ends
    bool executed;         // Whether the proposal was executed
    bool cancelled;        // Whether the proposal was cancelled
}
```

### Receipt

```solidity
struct Receipt {
    bool hasVoted;    // Whether the voter has voted
    bool support;     // true = for, false = against
    uint256 votes;    // Voting power used
}
```

Receipts are stored as a mapping: `proposalId → voter → Receipt`.

## Viewing Proposals

You can query indexed proposals via the GraphQL API — see [Get Proposals](/docs/api/dao/get-proposals) for the full reference. Filter by state, sort by `createdAt`, and paginate with `limit`/`offset`.

## On-Chain Proposal Check

```javascript
const proposal = await governance.getProposal(proposalId);
const { votesFor, votesAgainst, executed, cancelled, endTime } = proposal;
const isActive = await governance.isActive(proposalId);
const receipt = await governance.getReceipt(proposalId, voterAddress);
// receipt: { hasVoted, support, votes }
```
