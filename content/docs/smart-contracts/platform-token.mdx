## Overview

**PlatformToken** is the governance ERC20 token of the Slices protocol. It implements the standard ERC20 interface with an upgradeable UUPS proxy pattern and is used exclusively for staking and governance participation.

Unlike HOLD (the platform's utility token for pool operations and fees), PlatformToken has no on-chain conversion mechanism and serves a single purpose: **decentralized governance**. Holders stake PlatformTokens in the `DaoStaking` contract to gain voting power in the Slices DAO.

The contract inherits from OpenZeppelin's `ERC20Upgradeable` and is deployed behind an ERC1967 proxy, allowing logic upgrades through the protocol's governance mechanism.

## Standard ERC20 Functions

PlatformToken implements the full ERC20 interface:

| Function | Signature | Description |
|----------|-----------|-------------|
| `transfer` | `transfer(address to, uint256 amount) → bool` | Transfers tokens from the caller to another address. |
| `approve` | `approve(address spender, uint256 amount) → bool` | Allows a spender to withdraw tokens from the caller's balance. |
| `transferFrom` | `transferFrom(address from, address to, uint256 amount) → bool` | Transfers tokens using an allowance mechanism. |
| `balanceOf` | `balanceOf(address account) → uint256` | Returns the token balance of an account. |
| `allowance` | `allowance(address owner, address spender) → uint256` | Returns the remaining allowance for a spender. |

```solidity
// Standard transfer
function transfer(address to, uint256 amount) public virtual override returns (bool) {
    address owner = _msgSender();
    _transfer(owner, to, amount);
    return true;
}

// Standard approve
function approve(address spender, uint256 amount) public virtual override returns (bool) {
    address owner = _msgSender();
    _approve(owner, spender, amount);
    return true;
}
```

## Mint Function

PlatformToken has a single privileged function — `mint` — which is restricted to the protocol's **Governance** contract. This ensures that token supply is controlled entirely by the DAO.

| Function | Signature | Description | Access |
|----------|-----------|-------------|--------|
| `mint` | `mint(address[] calldata holders, uint256[] calldata amounts)` | Mints tokens to multiple addresses in a single transaction. | Governance |

```solidity
// Mint tokens to multiple holders (Governance only)
function mint(address[] calldata holders, uint256[] calldata amounts) external {
    addressBook.requireGovernance(msg.sender);
    for (uint256 i = 0; i < holders.length; i++) {
        _mint(holders[i], amounts[i]);
    }
}
```

The `mint` function accepts arrays of addresses and amounts, enabling batch distribution in a single transaction. Common use cases include:

- **Retroactive rewards** — for early platform participants
- **Airdrops** — to targeted communities
- **Staking incentives** — additional rewards deposited into the staking contract
- **Governance proposals** — the DAO can vote to mint tokens for any purpose

:::note
PlatformToken does **not** expose public `burn` or `burnFrom` functions. Token supply can only be increased through governance-approved minting. There is no built-in deflationary mechanism.
:::

## Staking

PlatformTokens must be staked in the `DaoStaking` contract to be used in governance. The staking mechanism is detailed in the [Staking](/docs/governance/staking) guide.

### Staking Flow

```solidity
// Approve PlatformToken for DaoStaking contract
function stake(uint256 amount) external nonReentrant
function unstake(uint256 amount) external nonReentrant
```

1. User approves the `DaoStaking` contract to spend their PlatformTokens.
2. User calls `stake(amount)` — tokens are transferred to the staking contract.
3. The staked amount is recorded and converted to voting power (1:1 ratio).
4. A staking timestamp is set, starting reward accrual.

```javascript
// Approve PlatformToken for DaoStaking contract
await platformToken.approve(daoStakingAddress, amount);

// Stake
await daoStaking.stake(amount);
```

### Staking Rewards

Rewards are calculated based on the annual reward rate set in the protocol's `Config` contract:

| Parameter | Value | Description |
|-----------|-------|-------------|
| `daoStakingAnnualRewardRate` | **10%** (1000 bps) | Annual staking reward rate |

```solidity
annualReward = stakedAmount × annualRewardRate / 10000
pendingReward = annualReward × stakingDuration / 365 days
```

For example, staking **50,000 PlatformToken** for **30 days**:

```
annualReward = 50,000 × 10% = 5,000 PlatformToken
pendingReward = 5,000 × 30 / 365 ≈ 410.96 PlatformToken
```

Rewards are automatically reinvested when the user stakes more or partially unstakes.

### Voting Lock

When a user votes on a proposal, `Governance.vote()` calls `DaoStaking.lock(user, proposal.endTime)`, which locks the user's staked tokens until the proposal's end time:

```solidity
function lock(address user, uint256 unlockTimestamp) external {
    addressBook.requireGovernance(msg.sender);
    require(stakedAmount[user] > 0, "No staked tokens");
    require(unlockTimestamp > block.timestamp, "Invalid unlock timestamp");

    // Only extends — never shortens
    if (unlockTimestamp > votingLockTimestamp[user]) {
        votingLockTimestamp[user] = unlockTimestamp;
    }
}
```

Key constraints:
- After voting, the user cannot unstake until the proposal's `endTime`.
- Voting on multiple proposals extends the lock to the latest `endTime`.
- The lock only extends — it never shortens.

## Role in DAO Governance

PlatformToken is the foundation of the Slices DAO. Staked tokens grant voting power that is used to approve or reject governance proposals.

### Voting Power

Voting power equals the staked PlatformToken balance (1:1 ratio):

```solidity
function getVotingPower(address user) external view returns (uint256) {
    return stakedAmount[user];
}
```

### Key Governance Parameters

| Parameter | Value | Description |
|-----------|-------|-------------|
| `proposalThreshold` | **1,000,000** PlatformToken | Minimum stake to create a proposal |
| `quorumPercentage` | **40%** (4000 bps) | Of total PlatformToken supply |
| `votingPeriod` | **7 days** | Duration of voting |
| `timelockDelay` | **2 days** | Delay before queued governance action executes |

All parameters are adjustable via Governance proposals through `Config.update*` functions.

### Proposal Lifecycle

```
Created → Voting Period → Auto-Executed or Auto-Cancelled
```

1. **Created** — a user with ≥ 1,000,000 staked PlatformTokens calls `propose()`.
2. **Voting** — stakers vote for or against during the 7-day voting period.
3. **Auto-execution** — if `votesFor >= quorum` AND `votesFor > votesAgainst`, the proposal executes immediately.
4. **Auto-cancellation** — if `votesAgainst >= quorum` AND `votesAgainst > votesAgainst`, the proposal is cancelled.

Quorum is calculated from the **total PlatformToken supply** (not just the staked amount):

```
quorum = platformToken.totalSupply() × quorumPercentage / 10000
```

For example, with `totalSupply = 10,000,000`:

| Parameter | Value |
|-----------|-------|
| totalSupply PlatformToken | 10,000,000 |
| Quorum (40%) | 4,000,000 votes |
| Voted "For" | 4,500,000 |
| Voted "Against" | 2,000,000 |
| Result | ✅ **PASSED** — 4.5M ≥ 4M and 4.5M > 2M |

See [Voting](/docs/governance/voting) and [Proposals](/docs/governance/proposals) for full details.

## Distribution and Supply

PlatformToken supply is entirely controlled by the DAO through the `mint` function. There is no fixed initial supply — tokens are minted as needed based on governance decisions.

### Common Distribution Methods

| Method | Description |
|--------|-------------|
| **Retroactive rewards** | Distributed to early platform participants via governance vote |
| **Airdrops** | Targeted distributions to communities |
| **Staking incentives** | Additional tokens deposited into `DaoStaking` as reward pool |
| **Governance proposals** | The DAO can vote to mint tokens for any purpose |

On testnet, PlatformTokens are available through the [Testnet Faucet](/docs/testnet-faucet/overview).

## Contract Architecture

PlatformToken is part of the **Platform** layer in the Slices protocol architecture:

```

│                    DAO Layer                         │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐          │
│  │Governance│  │ Timelock │  │ Treasury │          │
│  └────┬─────┘  └──────────┘  └──────────┘          │
│       │                                              │
│  ┌────▼─────┐                                       │
│  │DaoStaking│  ◄── stakes ──  PlatformToken         │
│  └──────────┘                                       │
├─────────────────────────────────────────────────────┤
│                  Platform Layer                      │
│  ┌──────────────┐  ┌──────────────────┐             │
│  │ PlatformToken│  │ReferralTreasury  │             │
```

The `AddressBook` contract stores the reference to PlatformToken and all other protocol contracts. PlatformToken is looked up by `DaoStaking` and `Governance` through `AddressBook`.

## Security Considerations

:::warning Access Control
The `mint` function is restricted to the **Governance** contract via `addressBook.requireGovernance(msg.sender)`. Only the DAO — through approved proposals — can mint new PlatformTokens. Unrestricted minting could lead to token supply inflation and dilution of voting power.

The `AddressBook.upgradeRole()` controls contract upgrades. This role should be held by the DAO's Timelock contract to ensure no single entity can unilaterally modify the token logic.
:::

:::note Upgradeability
PlatformToken is an upgradeable contract using the UUPS (Universal Upgradeable Proxy Standard) pattern. The proxy contract stores the state, while the implementation can be upgraded by the `AddressBook.upgradeRole()` holder. Always interact with PlatformToken through its proxy address. The implementation address can be updated only through a governance proposal.
:::

### Role Management

| Role | Privileges | Recommended Holder |
|------|------------|-------------------|
| `DEFAULT_ADMIN_ROLE` | Admin management | DAO Timelock |
| `AddressBook.upgradeRole()` | Upgrades | DAO Timelock |
| Governance access (via AddressBook) | Token minting | Governance contract |
