## Overview

**HoldToken** is a simple ERC20 utility token used within the RWA Platform ecosystem. It is **not upgradeable** and has a **fixed total supply** minted entirely in the constructor. The contract inherits only from OpenZeppelin's `ERC20` and does **not** include mint, burn, or access control functionality.

This token is intended for use as a utility token — for example, to pay platform fees or provide liquidity in an AMM. In production, the token name and symbol may be changed; the current code uses test values.

### Deployment context

In the **bscTestnet** network, the HoldToken contract is deployed at address `0x1c0e214bB702572E5582085d6E25c39A2B13510d` as a USDT mock (name `"USDT"`, symbol `"USD Test"`). It is used for testing functionality that requires USDT.

### Production note

On **BSC mainnet**, the real BSC USDT (`0x55d398326f99059fF775485246999027B3197955`) will be used instead of HoldToken. HoldToken is **not intended for production** — it is a test-only contract.

## Contract Source

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;

import { ERC20 } from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract HoldToken is ERC20 {
    constructor() ERC20("USDT", "USD Test") {
        _mint(msg.sender, 1_000_000_000_000_000 * 1e18);
    }
}
```

## Key Characteristics

- **Not upgradeable** — The contract is a plain ERC20 with no proxy or UUPS pattern.
- **Fixed supply** — All tokens are minted to the deployer at construction time. No additional minting or burning functions exist.
- **No access control** — There are no roles (`MINTER_ROLE`, `BURNER_ROLE`, etc.) and no dependency on `AddressBook` or `EventEmitter`.
- **Standard ERC20 interface** — Only the standard `transfer`, `approve`, `transferFrom`, `balanceOf`, and `allowance` functions are available.

## Role in Ecosystem

HoldToken serves as a utility token within the RWA Platform:

- **Fee payment** — Users may pay platform fees in HoldToken.
- **AMM liquidity** — HoldToken can be paired with other tokens in an automated market maker.
- **Staking / rewards** — If staking is implemented, HoldToken can be used as the staked asset (rewards would come from the fixed supply or external sources, not from minting).

:::note
Because the contract has no mint function, any reward distribution must rely on the existing supply (e.g., through transfers from a treasury address).
:::

## Security Considerations

- The entire supply is minted to the deployer. The deployer must distribute tokens appropriately (e.g., to a treasury, liquidity pool, or community allocation).
- No upgrade mechanism exists — the token logic is immutable after deployment.
- No burn function means the total supply cannot be reduced.
