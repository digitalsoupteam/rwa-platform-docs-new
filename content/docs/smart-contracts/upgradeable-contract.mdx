# UpgradeableContract

**UpgradeableContract** is the base contract for all upgradeable contracts in the RWA Platform protocol. It implements the UUPS (Universal Upgradeable Proxy Standard) pattern, allowing logic updates without changing the contract address. Every core contract — from `AddressBook` and `Config` to `Pool` and `RWA` — inherits from this foundation.

The contract combines OpenZeppelin's `Initializable`, `UUPSUpgradeable`, `OwnableUpgradeable`, and `AccessControlUpgradeable` to provide a secure, role-gated upgrade mechanism.

## Overview

The UUPS pattern places the upgrade logic in the implementation contract rather than the proxy. This means each contract is responsible for authorising its own upgrades. `UpgradeableContract` enforces this through a dedicated `upgradeRole` — an address that holds the exclusive right to call `upgradeTo` and `upgradeToAndCall`.

```solidity
abstract contract UpgradeableContract is
    Initializable,
    UUPSUpgradeable,
    OwnableUpgradeable,
    AccessControlUpgradeable
{
    bytes32 public constant UPGRADE_ROLE = keccak256("UPGRADE_ROLE");

    function uniqueContractId() public pure virtual returns (bytes32);
    function implementationVersion() public pure virtual returns (uint256);

    function _authorizeUpgrade(address newImplementation)
        internal
        virtual
        override
        onlyRole(UPGRADE_ROLE)
    {
        // Only UPGRADE_ROLE holders can authorise upgrades
    }
}
```

## Upgrade Role

### Role Definition

The `UPGRADE_ROLE` is a keccak256-hashed role identifier:

```solidity
bytes32 public constant UPGRADE_ROLE = keccak256("UPGRADE_ROLE");
```

Only addresses that hold this role can call `upgradeTo` or `upgradeToAndCall`. This is enforced by the `_authorizeUpgrade` function, which uses OpenZeppelin's `onlyRole` modifier.

### Granting and Revoking

The `UPGRADE_ROLE` is managed through the standard `AccessControlUpgradeable` interface:

| Function | Signature | Description | Access |
|----------|-----------|-------------|--------|
| `grantRole` | `grantRole(bytes32 role, address account)` | Grants the upgrade role to an account | `DEFAULT_ADMIN_ROLE` |
| `revokeRole` | `revokeRole(bytes32 role, address account)` | Revokes the upgrade role from an account | `DEFAULT_ADMIN_ROLE` |
| `renounceRole` | `renounceRole(bytes32 role, address account)` | Account renounces the role itself | Caller only |
| `hasRole` | `hasRole(bytes32 role, address account) → bool` | Check if an account has the role | Anyone |

```solidity
// Grant upgrade rights to a multisig wallet
grantRole(UPGRADE_ROLE, 0x1234...);

// Revoke upgrade rights from an old address
revokeRole(UPGRADE_ROLE, 0x5678...);

// Check if an address has upgrade rights
bool canUpgrade = hasRole(UPGRADE_ROLE, 0x1234...);
```

:::warning Role Management
The `DEFAULT_ADMIN_ROLE` holder has the power to grant and revoke `UPGRADE_ROLE`. This admin role should be held by a **multisig wallet** or a **timelock-governed contract**, never by a single EOA. Losing or compromising the admin role can lead to irreversible contract changes.
:::

### Recommended Configuration

| Role | Recommended Holder | Rationale |
|------|-------------------|-----------|
| `DEFAULT_ADMIN_ROLE` | Platform multisig / DAO Timelock | Controls all role assignments |
| `UPGRADE_ROLE` | Platform multisig | Authorises implementation upgrades |
| `UPGRADE_ROLE` (optional) | DAO Governance | Allows on-chain governance to vote on upgrades |

## Upgrade Mechanism (UUPS)

### How UUPS Works

Unlike the transparent proxy pattern, UUPS stores the upgrade function (`upgradeTo`) in the **implementation contract** rather than the proxy. This reduces proxy bytecode size and gas costs, but requires each new implementation to include the upgrade logic.

```
┌──────────────────────┐         delegatecall      ┌──────────────────────────┐
│       Proxy          │ ──────────────────────────►│   Implementation v1     │
│  (ERC1967Proxy)      │                             │  (UpgradeableContract)  │
│                      │                             │                         │
│  - implementation →  │                             │  - upgradeTo()          │
│  - storage (state)   │                             │  - mint()               │
└──────────────────────┘                             │  - burn()               │
                                                    └──────────┬───────────────┘
                                                               │ upgradeTo(v2)
                                                               ▼
                                                    ┌──────────────────────────┐
                                                    │   Implementation v2     │
                                                    │  (UpgradeableContract)  │
                                                    │                         │
                                                    │  - upgradeTo()          │
                                                    │  - mint()               │
                                                    │  - burn()               │
                                                    │  - newFeature()         │
                                                    └──────────────────────────┘
```

### Upgrade Functions

| Function | Signature | Description | Access |
|----------|-----------|-------------|--------|
| `upgradeTo` | `upgradeTo(address newImplementation)` | Upgrade to a new implementation | `UPGRADE_ROLE` |
| `upgradeToAndCall` | `upgradeToAndCall(address newImplementation, bytes memory data)` | Upgrade and call an initializer function | `UPGRADE_ROLE` |

```solidity
// Simple upgrade — new implementation must be compatible
upgradeTo(0xNewImplementationAddress);

// Upgrade with reinitialization
bytes memory initData = abi.encodeWithSelector(
    this.__NewContract_init.selector,
    param1,
    param2
);
upgradeToAndCall(0xNewImplementationAddress, initData);
```

:::note Storage Layout
UUPS requires that the **storage layout never changes** between implementations. New variables must be appended at the end of the existing storage, and existing variables must not be removed or reordered. Violating this rule will corrupt the proxy's state.
:::

## Access Control

`UpgradeableContract` inherits from both `OwnableUpgradeable` and `AccessControlUpgradeable`, providing two layers of access control:

### OwnableUpgradeable

Provides a simple `onlyOwner` modifier. The owner is set during initialization and can be transferred:

```solidity
// Set owner during initialization
function __UpgradeableContract_init(address owner) internal onlyInitializing {
    __Ownable_init(owner);
    __AccessControl_init();
}

// Transfer ownership
function transferOwnership(address newOwner) public override onlyOwner {
    super.transferOwnership(newOwner);
}
```

### AccessControlUpgradeable

Provides role-based access control (RBAC) with granular permissions:

| Role | Purpose | Default Admin |
|------|---------|---------------|
| `DEFAULT_ADMIN_ROLE` | Manages all roles (grant/revoke) | Owner |
| `UPGRADE_ROLE` | Authorises `upgradeTo` calls | Admin |

```solidity
// Grant a role
function grantRole(bytes32 role, address account) public override onlyRole(DEFAULT_ADMIN_ROLE) {
    _grantRole(role, account);
}

// Revoke a role
function revokeRole(bytes32 role, address account) public override onlyRole(DEFAULT_ADMIN_ROLE) {
    _revokeRole(role, account);
}
```

### Reinitializer

OpenZeppelin's upgradeable contracts use a versioned initializer system. The `initializer` modifier can only be called once per contract lifetime. For subsequent upgrades that need to set new state variables, use `reinitializer`:

```solidity
// Initial deployment — called once
function initialize(address owner) public initializer {
    __UpgradeableContract_init(owner);
    __Ownable_init(owner);
    __AccessControl_init();
    _grantRole(DEFAULT_ADMIN_ROLE, owner);
    _grantRole(UPGRADE_ROLE, owner);
}

// Upgrade v1 → v2 — adds a new parameter
function initializeV2(uint256 newParam) public reinitializer(2) {
    _newParam = newParam;
}

// Upgrade v2 → v3 — adds another parameter
function initializeV3(address additionalContract) public reinitializer(3) {
    _additionalContract = additionalContract;
}
```

| Modifier | Version | When to Use |
|----------|---------|-------------|
| `initializer` | 1 | First deployment only |
| `reinitializer(2)` | 2 | First upgrade that needs state changes |
| `reinitializer(3)` | 3 | Second upgrade with state changes |
| `reinitializer(N)` | N | Subsequent upgrades |

:::warning Reinitializer Safety
Each `reinitializer(N)` can only be called once per version `N`. If a reinitializer function needs to be called again (e.g., after a failed upgrade), a new version number must be used. Always increment the version number for each upgrade that modifies state.
:::

## Inheritance

### How to Use in Child Contracts

Any contract that needs upgradeability should inherit from `UpgradeableContract` and follow this pattern:

```solidity
contract MyNewContract is UpgradeableContract {
    // Custom state variables
    uint256 public myValue;
    address public myAddress;

    // Unique identifier for this contract type
    bytes32 public constant override uniqueContractId = keccak256("MyNewContract");

    // Version tracking
    uint256 public constant override implementationVersion = 1;

    // Initializer (not constructor!)
    function initialize(
        address owner,
        uint256 initialValue,
        address initialAddress
    ) public initializer {
        __UpgradeableContract_init(owner);
        myValue = initialValue;
        myAddress = initialAddress;
    }

    // Custom functions
    function setValue(uint256 newValue) external onlyRole(DEFAULT_ADMIN_ROLE) {
        myValue = newValue;
    }

    // Upgrade v2 initializer
    function initializeV2(address newParam) public reinitializer(2) {
        _newParam = newParam;
    }
}
```

### Required Overrides

Every child contract **must** override:

| Function | Returns | Description |
|----------|---------|-------------|
| `uniqueContractId()` | `bytes32` | Unique keccak256 identifier for the contract type |
| `implementationVersion()` | `uint256` | Current implementation version number |

### Deployment Flow

1. **Deploy implementation** — the logic contract (e.g., `MyNewContract`)
2. **Deploy proxy** — an `ERC1967Proxy` pointing to the implementation
3. **Initialize** — call `initialize()` through the proxy (not the implementation directly)
4. **Upgrade** — deploy a new implementation, then call `upgradeTo()` through the proxy

```solidity
// Step 1: Deploy implementation
MyNewContract implementation = new MyNewContract();

// Step 2: Deploy proxy
ERC1967Proxy proxy = new ERC1967Proxy(
    address(implementation),
    abi.encodeWithSelector(
        MyNewContract.initialize.selector,
        owner,
        1000,
        address(0x1234)
    )
);

// Step 3: Interact through proxy
MyNewContract contract = MyNewContract(address(proxy));
contract.setValue(2000);

// Step 4: Upgrade
MyNewContract v2 = new MyNewContractV2();
contract.upgradeTo(address(v2));
```

:::note Always Use the Proxy
Never call `initialize` or any state-changing function directly on the implementation contract. The implementation holds no state — all data lives in the proxy. Direct calls to the implementation will either revert (if `initializer` was already used) or corrupt the implementation's own storage.
:::

## Security Considerations

:::warning Upgrade Role Compromise
If the `UPGRADE_ROLE` is granted to a malicious or compromised address, the entire contract can be upgraded to arbitrary logic. This could drain funds, freeze assets, or alter core protocol behaviour. Always use a **multisig wallet** or **timelock-governed contract** for this role.
:::

:::note Storage Collisions
When upgrading, ensure that new implementation contracts do not introduce storage variables that overlap with existing ones. Follow OpenZeppelin's storage gap pattern:

```solidity
// Reserve storage slots for future upgrades
uint256[50] private __gap;
```
:::

### Role Summary

| Role | Privileges | Risk if Compromised | Recommended Holder |
|------|------------|---------------------|-------------------|
| `DEFAULT_ADMIN_ROLE` | Grant/revoke any role | Total loss of control | Multisig / DAO Timelock |
| `UPGRADE_ROLE` | Authorise `upgradeTo` | Arbitrary code execution | Multisig |
| Owner (Ownable) | Transfer ownership | Ownership hijack | Multisig / DAO |
