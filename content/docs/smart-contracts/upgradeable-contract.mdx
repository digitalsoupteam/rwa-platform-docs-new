# UpgradeableContract

**UpgradeableContract** is the base contract for all upgradeable contracts in the RWA Platform protocol. It implements the UUPS (Universal Upgradeable Proxy Standard) pattern, allowing logic updates without changing the contract address. Every core contract — from `AddressBook` and `Config` to `Pool` and `RWA` — inherits from this foundation.

The contract combines OpenZeppelin's `Initializable`, `UUPSUpgradeable`, and `ReentrancyGuardUpgradeable` to provide a secure, role-gated upgrade mechanism. Upgrade authorization is delegated to the `AddressBook` contract via the `_verifyAuthorizeUpgradeRole()` function.

## Overview

The UUPS pattern places the upgrade logic in the implementation contract rather than the proxy. This means each contract is responsible for authorising its own upgrades. `UpgradeableContract` enforces this through a dedicated upgrade role managed by the `AddressBook` — an address that holds the exclusive right to call `upgradeTo` and `upgradeToAndCall`.

```solidity
abstract contract UpgradeableContract is
    Initializable,
    UUPSUpgradeable,
    ReentrancyGuardUpgradeable
{
    function uniqueContractId() public pure virtual returns (bytes32);
    function implementationVersion() public pure virtual returns (uint256);

    function _authorizeUpgrade(address newImplementation)
        internal
        virtual
        override
    {
        _verifyAuthorizeUpgradeRole();
    }

    function _verifyAuthorizeUpgradeRole() internal view virtual {
        // Delegates to AddressBook to check if msg.sender has upgrade rights
        require(
            IAddressBook(addressBook).upgradeRole(msg.sender),
            "UpgradeableContract: caller does not have the upgrade role"
        );
    }
}
```

## Upgrade Authorization via AddressBook

### How It Works

Instead of storing roles directly in the contract (as in `AccessControlUpgradeable`), `UpgradeableContract` relies on the **AddressBook** — a central registry that manages all protocol roles, including the upgrade role. The `_verifyAuthorizeUpgradeRole()` function queries the `AddressBook` to check whether `msg.sender` holds the upgrade role.

```solidity
function _verifyAuthorizeUpgradeRole() internal view virtual {
    require(
        IAddressBook(addressBook).upgradeRole(msg.sender),
        "UpgradeableContract: caller does not have the upgrade role"
    );
}
```

The `AddressBook` contract exposes a function `upgradeRole(address account) → bool` that returns `true` if the account is authorised to perform upgrades. This role is managed by the `AddressBook` itself, typically through a multisig or governance process.

### Why AddressBook?

- **Single source of truth** for all protocol roles — no duplication across contracts.
- **Simplified role management** — grant or revoke upgrade rights in one place.
- **Consistent security** — all upgradeable contracts share the same authorization logic.

## Inheritance

### How to Use in Child Contracts

Any contract that needs upgradeability should inherit from `UpgradeableContract` and follow this pattern:

```solidity
contract MyNewContract is UpgradeableContract {
    // Custom state variables
    uint256 public myValue;
    address public myAddress;

    // Unique identifier for this contract type
    bytes32 public constant override uniqueContractId = keccak256("MyNewContract");

    // Version tracking
    uint256 public constant override implementationVersion = 1;

    // Initializer (not constructor!)
    function initialize(
        address owner,
        uint256 initialValue,
        address initialAddress
    ) public initializer {
        __UpgradeableContract_init();
        myValue = initialValue;
        myAddress = initialAddress;
    }

    // Custom functions
    function setValue(uint256 newValue) external {
        myValue = newValue;
    }
}
```

### Required Overrides

Every child contract **must** override:

| Function | Returns | Description |
|----------|---------|-------------|
| `uniqueContractId()` | `bytes32` | Unique keccak256 identifier for the contract type |
| `implementationVersion()` | `uint256` | Current implementation version number |

### Initialization

The base `__UpgradeableContract_init()` function is called during the child's initializer. It sets up the `AddressBook` reference and initializes `UUPSUpgradeable` and `ReentrancyGuardUpgradeable`.

```solidity
// Inside UpgradeableContract
function __UpgradeableContract_init() internal onlyInitializing {
    __UUPSUpgradeable_init();
    __ReentrancyGuard_init();
}
```

## Upgrade Mechanism (UUPS)

### How UUPS Works

Unlike the transparent proxy pattern, UUPS stores the upgrade function (`upgradeTo`) in the **implementation contract** rather than the proxy. This reduces proxy bytecode size and gas costs, but requires each new implementation to include the upgrade logic.

```
┌──────────────────────┐         delegatecall      ┌──────────────────────────┐
│       Proxy          │ ──────────────────────────►│   Implementation v1     │
│  (ERC1967Proxy)      │                             │  (UpgradeableContract)  │
│                      │                             │                         │
│  - implementation →  │                             │  - upgradeTo()          │
│  - storage (state)   │                             │  - mint()               │
└──────────────────────┘                             │  - burn()               │
                                                    └──────────┬───────────────┘
                                                               │ upgradeTo(v2)
                                                               ▼
                                                    ┌──────────────────────────┐
                                                    │   Implementation v2     │
                                                    │  (UpgradeableContract)  │
                                                    │                         │
                                                    │  - upgradeTo()          │
                                                    │  - mint()               │
                                                    │  - burn()               │
                                                    │  - newFeature()         │
                                                    └──────────────────────────┘
```

### Upgrade Functions

| Function | Signature | Description | Access |
|----------|-----------|-------------|--------|
| `upgradeTo` | `upgradeTo(address newImplementation)` | Upgrade to a new implementation | Upgrade role (via AddressBook) |
| `upgradeToAndCall` | `upgradeToAndCall(address newImplementation, bytes memory data)` | Upgrade and call an initializer function | Upgrade role (via AddressBook) |

```solidity
// Simple upgrade — new implementation must be compatible
upgradeTo(0xNewImplementationAddress);

// Upgrade with reinitialization
bytes memory initData = abi.encodeWithSelector(
    this.__NewContract_init.selector,
    param1,
    param2
);
upgradeToAndCall(0xNewImplementationAddress, initData);
```

:::note Storage Layout
UUPS requires that the **storage layout never changes** between implementations. New variables must be appended at the end of the existing storage, and existing variables must not be removed or reordered. Violating this rule will corrupt the proxy's state.
:::

### Deployment Flow

1. **Deploy implementation** — the logic contract (e.g., `MyNewContract`)
2. **Deploy proxy** — an `ERC1967Proxy` pointing to the implementation
3. **Initialize** — call `initialize()` through the proxy (not the implementation directly)
4. **Upgrade** — deploy a new implementation, then call `upgradeTo()` through the proxy

```solidity
// Step 1: Deploy implementation
MyNewContract implementation = new MyNewContract();

// Step 2: Deploy proxy
ERC1967Proxy proxy = new ERC1967Proxy(
    address(implementation),
    abi.encodeWithSelector(
        MyNewContract.initialize.selector,
        owner,
        1000,
        address(0x1234)
    )
);

// Step 3: Interact through proxy
MyNewContract contract = MyNewContract(address(proxy));
contract.setValue(2000);

// Step 4: Upgrade
MyNewContract v2 = new MyNewContractV2();
contract.upgradeTo(address(v2));
```

:::note Always Use the Proxy
Never call `initialize` or any state-changing function directly on the implementation contract. The implementation holds no state — all data lives in the proxy. Direct calls to the implementation will either revert (if `initializer` was already used) or corrupt the implementation's own storage.
:::

## Security Considerations

:::warning Upgrade Role Compromise
If the upgrade role in the `AddressBook` is granted to a malicious or compromised address, the entire contract can be upgraded to arbitrary logic. This could drain funds, freeze assets, or alter core protocol behaviour. Always use a **multisig wallet** or **timelock-governed contract** for this role.
:::

:::note Storage Collisions
When upgrading, ensure that new implementation contracts do not introduce storage variables that overlap with existing ones. Follow OpenZeppelin's storage gap pattern:

```solidity
// Reserve storage slots for future upgrades
uint256[50] private __gap;
```
:::

### Role Summary

| Role | Privileges | Risk if Compromised | Recommended Holder |
|------|------------|---------------------|-------------------|
| Upgrade role (in AddressBook) | Authorise `upgradeTo` | Arbitrary code execution | Multisig / DAO Timelock |
