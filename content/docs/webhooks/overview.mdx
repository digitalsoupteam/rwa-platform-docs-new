# Webhooks

Webhooks allow you to receive real-time HTTP notifications when events happen on the Slices platform — pools created, tokens minted/burned, proposals executed, and more. Instead of polling the GraphQL API, register a webhook endpoint and let the platform push events to your server.

## How It Works

```
Platform Event → Webhooks Service → RabbitMQ → Delivery Daemon →
HTTP POST to your URL (with HMAC signature) → Your server processes it
```

1. You register a webhook endpoint with a URL, event types, and optional rate limit
2. A `secret` is generated for HMAC signature verification — store it securely
3. When a subscribed event occurs, the webhooks service enqueues a delivery
4. The delivery daemon sends an HTTP POST to your URL with the event payload
5. The payload is signed with HMAC-SHA256

## Available Events

| Event | Description |
|---|---|
| `pool.created` | A new pool has been created |
| `pool.staked` | A participant has staked tokens in a pool (mint) |
| `pool.closed` | A pool has been closed |
| `business.created` | A new business has been created |
| `business.updated` | A business has been updated |
| `business.deleted` | A business has been deleted |
| `token.minted` | New tokens have been minted |
| `token.burned` | Tokens have been burned |
| `proposal.executed` | A governance proposal has been executed |
| `proposal.rejected` | A governance proposal has been rejected |

## Payload Structure

Each webhook delivery sends an HTTP POST request with a JSON body containing the event details. The payload has the following structure:

| Field | Type | Description |
|---|---|---|
| `id` | `String` | Unique identifier for the event |
| `type` | `String` | The event type (e.g., `pool.created`) |
| `timestamp` | `Float` | Unix timestamp in milliseconds when the event occurred |
| `data` | `Object` | Event-specific payload (varies by event type) |

### Example Payload

```json
{
  "id": "evt_abc123def456",
  "type": "pool.created",
  "timestamp": 1712345678000,
  "data": {
    "poolId": "pool_xyz789",
    "name": "Real Estate Fund A",
    "creatorId": "user_001",
    "createdAt": 1712345678000
  }
}
```

The `data` object contains fields relevant to the specific event. Refer to the individual event documentation for detailed schemas.

## Creating a Webhook Endpoint

To start receiving webhooks, you need to create a webhook endpoint using the GraphQL API. Use the `createWebhookEndpoint` mutation.

### GraphQL Mutation

```graphql
mutation CreateWebhookEndpoint($input: CreateWebhookEndpointInput!) {
  createWebhookEndpoint(input: $input) {
    id
    url
    events
    description
    active
    rateLimitPerMinute
    secret
    createdAt
  }
}
```

### Variables

```json
{
  "input": {
    "url": "https://your-server.com/webhook-handler",
    "events": ["pool.created", "pool.staked", "token.minted"],
    "description": "My production webhook",
    "rateLimitPerMinute": 60
  }
}
```

The `secret` field is returned only once upon creation. Store it securely to verify incoming webhook signatures.

## Testing Webhooks

Before deploying to production, test your webhook integration using the following approaches:

### Using a Test Endpoint

1. Create a temporary endpoint using a service like [webhook.site](https://webhook.site) or [RequestBin](https://requestbin.com).
2. Register the test URL as a webhook endpoint (see [Creating a Webhook Endpoint](#creating-a-webhook-endpoint)).
3. Trigger an event (e.g., create a pool) and observe the incoming request on the test endpoint.
4. Verify the payload structure and signature.

### Simulating Events

You can simulate events by performing actions in the platform (e.g., minting tokens, creating a business) and checking if your endpoint receives the corresponding webhook.

### Verifying Signatures Locally

Use the provided `verifyWebhook` function (see [Payload Verification](#payload-verification)) to test signature validation with sample payloads.

### Common Issues

- **Timeout:** Ensure your endpoint responds within 10 seconds.
- **Non-2xx response:** Return a 2xx status code (e.g., 200) to acknowledge receipt.
- **Duplicate deliveries:** Implement idempotency using the `X-Webhook-Id` header.

## Payload Verification

Every webhook delivery includes headers for verification:

| Header | Description |
|---|---|
| `X-Webhook-Id` | Unique event ID |
| `X-Webhook-Timestamp` | Delivery timestamp (ms) |
| `X-Webhook-Signature` | `sha256=` + HMAC-SHA256 of the request body, signed with your secret |

Verify the signature on your server to confirm the payload is from Slices:

```javascript
import crypto from 'crypto';

function verifyWebhook(rawBody, signature, secret) {
  const expected = crypto.createHmac('sha256', secret).update(rawBody).digest('hex');
  return `sha256=${expected}` === signature;
}
```

## Delivery & Retries

- **Timeout** — each delivery attempt has a 10-second timeout
- **Retries** — failed deliveries are retried with exponential backoff (up to 128 seconds between retries)
- **Dead letter** — if all retries fail, the delivery is marked as `dead_letter` and stops
- **Rate limiting** — each endpoint has a configurable `rateLimitPerMinute`

## Best Practices

- **Verify signatures** — always check the `X-Webhook-Signature` header to confirm authenticity
- **Respond quickly** — return a 2xx status code fast; process the event asynchronously if needed
- **Handle duplicates** — events may be delivered more than once; use `X-Webhook-Id` for deduplication
- **Store the secret securely** — it is returned only once at creation
- **Monitor delivery logs** — check the dead letter queue for failed deliveries
- **Test your integration** — use test endpoints and simulate events before going live.
